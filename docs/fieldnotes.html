I. The project

Two engines, one spec, thirteen years, a few dozen people.

History · 2013 → 2026

Thirteen years in one timeline

MapLibre's two engines share a 2013–2014 Mapbox origin, split from each other twice (2021 and 2023), and in 2026 are porting each other's architecture back and forth.

The web renderer came first: mapbox-gl-js was created on 2013-03-07 and its first commit, "first version of gl renderer", landed on 2013-06-26. The native renderer started on 2014-01-07, and its third commit ever was "emscripten support": the C++ port briefly targeted the browser before that was removed on 2014-02-21. Twelve years later Native is back in the browser through WebGPU #4370, while the 2024 issue asking for a WASM port is still open #2554.

Most of Native's runtime architecture is Mapbox-era (2015–2019): StyleUpdateParameters, the actor model for tile workers, immutable style Impl snapshots, the RendererFrontend split and RenderOrchestrator. Mapbox-era mapbox-gl-native pulled mapbox-gl-js in as a git submodule for shaders, the style-spec reference and integration tests (last bump 2020-02-10; MapLibre removed it on 2021-01-21 and later dropped its maplibre-gl-js submodule in #938).

In December 2020 Mapbox relicensed GL JS v2 and MapLibre forked both engines. On 2020-12-16 Petr Pokorny (MapTiler) assembled the Native monorepo by re-merging the three repositories Mapbox had split apart in 2019.

After the fork Native was nearly dormant (198 commits in 2021, one Android release in 2022) until an AWS-funded contract with Stamen Design and Wet Dog Weather produced the drawables architecture and a native Metal backend. In March 2023 Native removed the maplibre-gl-js submodule #938: from then on the two codebases shared no build-time link. Native went multi-backend (Vulkan 2024, WebGPU 2025) and shipped native-first features: HarfBuzz shaping, PMTiles, the Action Journal, MLT.

GL JS went through five majors: TypeScript (v2), WebGL2 (v3), Promises (v4), globe (v5), ESM-only (v6). Its 2026 rebuild explicitly follows Native's drawable/tweaker design #7640, and its WebGPU proof of concept was a port of Native's backend back into TypeScript #7411.

2026 is the year everything accelerated: mbgl → mln, the first C plugin ABI, HarmonyOS, a +43k-line globe port with pre-releases on 2026-10-08, a 145-issue sweep in GL JS, and a large share of AI-assisted PRs.

GitHub · issue trackers

What the issue trackers are asking for

Native has 514 open issues and GL JS has 258. The most-wanted items on both sides are about projections: globe and terrain on Native, arbitrary CRS on GL JS. Native's backlog is dominated by Android crashes and lifecycle bugs; GL JS's by terrain and symbols.

Native. The backlog grew from 66 open issues at the end of 2021 to 514 today; 2024 was the only year closures exceeded openings (381 vs 368). Labels are platform-first, not problem-first: android is on 167 open issues and bug on 2. 36% of open issues have no label at all, so triage effectively happens by platform owner [inferred]. 70 open titles read like crashes; 48 of them are Android. A globe style currently renders flat on Native with no error, because the parser does not read projection and the spec's projection property has no sdk-support table to reveal it.

GL JS. 64% of open issues carry "PR is more than welcomed", which in practice means "accepted, nobody assigned". There is no project board; planning lives in tracking issues (#7640 GM, #8694 CSC), the roadmap site and a monthly meeting. The six oldest open issues all date from the first seven months after the fork (2020-12-28 to 2021-06-24) and are Mapbox-era carry-overs. In 2026, once v6 allowed breaking changes, GL JS closed several 3–5-year-old structural issues: ESM, tree shaking, feature altitude, layer opacity, nested GeoJSON, long-press.

      Process · design-proposals/

      Native's design proposals and what became of them

      design-proposals/ holds 8 proposals and a template, from 2022 to 2025. Two were paid for and largely built (drawables and Metal). One was built then superseded, one built recently and only for Android; the rest are partial, abandoned, or have code unmerged for almost three years. The 2026 proposals (globe, the C plugin roadmap) never got a file in the directory at all.

      The two proposals that shaped the codebase came from one paid contract (Stamen Design with Wet Dog Weather, for AWS). Rendering Modularization brought the drawables/builders vocabulary from WhirlyGlobe-Maply with eight evaluation metrics, including "binary should not increase more than 5%". The Metal Port proposal says outright: "You might say 'oh, we'll do indirect later', but you won't." Four years on, neither indirect command buffers nor heaps exist in the Metal backend.

      The modularization proposal also promised developer-facing hooks (replace shaders, replace layer rendering) that were never exposed: onRegisterShaders is a no-op on iOS and Android, and CustomDrawableLayer was added in 2023 and removed in September 2026. The C plugin ABI is the second attempt at the same goal. The 2026 work moved design discussion into PR bodies.

        Downstream

        Who builds on what

        Two renderers, one spec and about forty downstream projects. Each edge is a dependency, a pin or a codegen step. The cross-platform SDKs each stitch two or three engines behind one API.

        The ecosystem sits in three integration tiers. Bindings straight onto the C++ core (about ten: Android JNI, Darwin ObjC++, Node (still NAN), Qt, OpenHarmony, GLFW, maplibre-native-rs, maplibre-native-ffi, Slint, the Flutter playground's own C ABI).         Downstream latency

        A feature's trip downstream

        Feature state reached the native core in 2019. It reached the Android SDK in July 2026, iOS in September 2026, and Flutter on iOS still hasn't got it. Each hop has its own release train and its own pin.

        Shipping a style feature to a cross-platform app user takes a spec PR, the GL JS implementation, a native core port (the core keeps a hand-edited copy of v8.json), an Android API, an iOS API, two separate releases (13.x and 6.x), a wrapper pin bump, the wrapper's API and its docs. Any step can stall. The lag runs both ways: distance was native-first (iOS 5.9.0, 2020) and reached GL JS in 4.2.0 (2024); font-faces and rounded-corner extrusions shipped on Native first. Put simply, the direction of lag follows who funds the work [inferred].

        Duplication

        Everyone regenerates the same things

        Seven style-property code generators. Six annotation systems. Five user-location stacks. Seven gesture engines. More than ten bindings onto one C++ core. All of them read the same v8.json or wrap the same two engines.

        The largest generated or hand-mirrored files measure the cost: RN's MLRNStyleFactory.kt (95 KB) and MLRNStyle.m (72 KB); Flutter's layer_properties.dart (96 KB) plus hand-mirrored Java (34 KB) and Swift (30 KB) converters; the Flutter playground's flmln_style_gen.cpp (198 KB); Android's 9,328 lines of generated per-layer Java and 4,381 lines of generated JNI C++. The FFI replaces all of this with one generic setter that takes style-spec JSON, mln_map_set_layer_property(map, layer, name, json), which also covers plugin layers.

        N implementations, downstream edition
        C ABI

        maplibre-native-ffi: the embedding API upstream never had

        A C ABI with 319 exported functions, 8 language bindings and 17 build environments over about 40k lines of C++ glue. A Hosted-tier project with 30 stars that in 2026 became the most aggressive bug-finding harness MapLibre Native has.

        The model has three objects concepts.md: a Runtime (scheduler and event storage, one per owner thread), a Map (style, camera, sources; no graphics) and a RenderSession (one map into one target: native surface, owned texture or borrowed texture, on Metal, Vulkan, OpenGL or WebGPU). The README states the scope rule every SDK in the ecosystem was missing: "Framework concerns such as gestures, widgets, declarative UI, and application lifecycle integration belong in downstream adapters".

        The GitHub repo dates from 2025-01-07; the current history starts 2026-04-26 with "pivot design to universal C ABI" (647 commits, 179 issues, 612 PRs). The motive is in native discussion #4286: "Main problem for MapLibre Compose was the varying API surfaces across MapLibre Native Android and iOS". mln_c_version() returns 0 while the ABI is unstable, and releases use calendar ABI versions API_EPOCH.YYYYMM.REVISION (e.g. 0.202610.0) where epoch 0 means "no promise" versioning.md.

        C ABI design principles

        How it wraps the core

        Every glue class below is a workaround for an upstream assumption, and the code comments say so directly. The FFI's comments also document three pipeline-cache hazards in upstream's backends: Metal "caches render pipeline states under a key that omits the color format" metal_texture_backend.mm:272; Vulkan "keys its pipeline cache on the render pass handle, so destroying the pass strands every cached pipeline" vulkan_surface_session.cpp:239; WebGPU "reads the color format off the target … but does not key its cache on it" webgpu_texture_session.cpp:263.

        Threading: a display-paced frame loop

        Upstream's mln::Map is thread-affine and driven by a host-pumped RunLoop. The FFI had to add a budgeted pump (patch 0003, upstream #4577), a wake source (ffi#352: setPlatformCallback "fires from RunLoop::push while the RunLoop mutex is held … from arbitrary threads"), and mailboxes that move renderer callbacks back to the map thread. Below: FFI on main, one host thread doing display, runtime and render-session work.

        The redesign moves execution into the native layer. ffi#631 (+112,342/−108,023, 874 files) is closed; ffi#760 "Move execution into the native core and generate language bindings" is an open draft at +285,918/−298,756 across 2,151 files. Its model: "The runtime owns one native scheduler thread … Any host thread can submit runtime and map work." Map mutations are commands with completions that carry generations; "Snapshot reads never call into mutable MapLibre map state."

        Field report from jfberry, who runs the rampardos production Go tile renderer on this lineage: "the port compiled and passed our race-enabled unit + integration suites on the first run … easiest of the four migrations"; time-to-first-frame-result was sub-ms in 54 of 56 production renders. A review of #631 criticised the event path: "Three mechanisms … do one job." Compose still runs its own owner-thread queue on raw pthreads because "MapLibre's thread-affine, host-pumped execution model is what puts the host on raw threads at all" MlnFfiOwnerThread.kt.

          Case study

          maplibre-compose: from four engine adapters to two

          In 12 days of August 2026, maplibre-compose moved desktop, Android and iOS off the official SDKs and onto one shared Kotlin adapter over the C ABI. Its actual declarations fell from about 754 to about 260 and about 80 issues closed. The cost: a third thread and a 34% CPU gap on one camera tour.

          Motive. compose#572 wanted to "eliminate API differences between the different SDKs". Before the migration each of the 11 layer types had its own actual file per platform mapping properties onto each SDK's typed setters. Timeline: plan #833 (07-22); desktop #834 merged 08-08 (+21,484/−7,324); shared actuals #932 08-17; Android #844 08-19; iOS #985 08-20. StreetComplete then migrated SC#7088, and Compose shipped v0.15 → v0.20 in five weeks.

          The new shape. internal interface MapAdapter (~35 members) has exactly two implementations: MlnFfiMapSession (Android, iOS, macOS, JVM) and GlJsMapSession (web). Gestures and ornaments live in common Compose code, which removed the 300 ms SDK tap delay #829 and the heavyweight-view z-order problems #184. Divergence is built into the public API: options differing by source set are expect classes, and unsupported writes throw api-guidelines.md. Engine limits are tracked in #1639 (Native) and #1718 (GL JS).

          Extensibility

          One plugin, two engines, about three times the code on the web

          The new upstream C plugin ABI lets the core own property evaluation, transitions, tile layout and queries. GL JS offers only a raw gl custom layer, so the web twin of every plugin reimplements the paint engine and reads GL JS internals (particles: 8,857 TS + 2,183 paint vs 4,932 Zig).

          sargunv/maplibre-plugins (created 2026-09-23; README: "Vibe-coded. Not fit for use.") exercises include/mln/plugin/plugin_api.h (520 lines) from #4612, extended by #4654, #4663, #4665, #4692. The backend bitmask is OPENGL | VULKAN | METAL with no WebGPU: "a WebGPU build registers a plugin but has no shader path for its layers."

          Each plugin has a shared spec.json contract and shared GLSL that a Zig build splices into GL GLSL, Vulkan GLSL and a separate MSL string, mirrored to JS. On the GL JS side, @maplibre-plugins/paint (2,183 lines) reimplements paint compilation and Native's transition semantics ("300 ms, ease (0, 0, 0.25, 1) …"), and tile data comes from map.style.tileManagers: "None of them is public API … each access checks the shape it relies on and throws one GlJsInternalsError".

          Cautionary tales

          maplibre-rs, Navara, Galileo: three Rust engines, one spec

          maplibre-rs had one author and stalled; even so, its biggest module is a line-by-line translation of Native's symbol layout. Navara and Galileo are the next attempts. Each one shows that the style spec, not any engine, is what the ecosystem actually shares.

          maplibre-rs (created 2021-11-28; 1.07 MB of Rust, 25 KB of WGSL) is candid: "It is unclear whether the high-performance requirements of rendering maps using vector graphics are achievable using the current stack." README. Architecture: a Bevy-derived render graph (Extract → Prepare → Queue → PhaseSort → Render → Cleanup), a per-tile mini-ECS, a compile-time Kernel<E: Environment> per platform, lyon tessellation. Its largest module, legacy/ (319 KB), is hand-translated C++: symbol_layout.rs opens with "Translated from …maplibre-native/blob/4add9ea/…" and legacy/mod.rs with #![allow(unused)].

          Navara (reearth → maplibre/navara, 379 stars) was onboarded through maplibre#509: "a headless GIS core, independent of the rendering engine… Rust/WebAssembly" with drawing delegated to Three.js; style-spec support at onboarding was scaffolding plus a fill layer. sjg-wdw: "There's no community in common, no real code in common, no users in common." Galileo (651 stars; wgpu, lyon, rustybuzz) has a WIP galileo-maplibre crate and one maintainer with 257 commits (next: 10). rustybuzz has since been archived in favour of HarfRust. A third Rust engine implementing the spec independently suggests the spec is the ecosystem's real product [inferred].

                Tile format

                MLT: a columnar format that stops being columnar at Point[][]

                Both renderers decode MapLibre Tiles and immediately rebuild MVT-shaped, per-feature objects, discarding the layout MLT was designed around. Its own benchmarks show that once both are gzipped, the median tile decodes slower than MVT (117% on OpenMapTiles, 113% on Protomaps).

                Design. A tile is a sequence of frames with a format tag (0x01 v1, stable Oct 2025; 0x02 v2, experimental); decoders skip unknown tags. Each layer is a FeatureTable whose columns split into Present/Data/Length/Offset streams, with delta, RLE, dictionary, bit-packing, FastPFOR, FSST, ALP and rANS encodings and optional pre-tessellation. "As with MVT, the tile grid, map projection, and anything else outside one tile are out of its scope": MLT does not help with Web Mercator coupling. Paper: Tremmel & Zink, SIGSPATIAL '25.

                Single core or two engines? Everyone else's answer

                Every mapping vendor we could check that ships both web and native products kept two engines (Apple and Google [inferred]). Shared cores compiled to wasm work at Figma and Google Earth, and in one small mapping SDK. The open engines that died (harp.gl, Tangram, CARTO, maplibre-rs) failed on people and funding, not code [inferred].

                Mapbox never unified web and native code; it unified the test corpus. GL JS v3 is still TypeScript, but its render suite (3,114 tests) runs on native runners under platform tags such as native-android-vulkan-mali with expected-native*.png baselines. MapLibre has 1,718 (GL JS) and 1,337 (Native) render tests in separate forked suites. Esri builds all native SDKs on one C++ core → C++ API → C ABI → per-language interop, almost exactly maplibre-native-ffi's layering.

                Tangram (Mapzen) is the closest analog: a JS engine and a C++ engine with a "nearly interchangeable" YAML scene format; scene files could contain JavaScript, so Tangram-ES embedded Duktape and JavaScriptCore. Mapzen shut down in Jan 2018. Figma went asm.js → wasm in 2017 and to WebGPU through Dawn + emdawnwebgpu in 2025, with a mid-session WebGL fallback: the path MapLibre Native is now on. Dropbox abandoned shared C++: "more expensive than just writing the code twice" (UI-heavy logic, a different share ratio [inferred]).

                  Native in the browser: ~10× the payload, plus headers no embed can set

                  maplibre-native-ffi builds MapLibre Native for emscripten-wasm32 on WebGL2 and WebGPU, and CI is green in headless Chromium. It ships 2.2 MB brotli against GL JS's 247 KB, needs cross-origin isolation and a fixed 512 MB heap, and for WebGPU needs JSPI, which Safari lacks.

                  • Build wiring mln_ffi_emscripten.cmake: -pthread and -fwasm-exceptions directory-wide; PTHREAD_POOL_SIZE=16, INITIAL_MEMORY=512MB, no ALLOW_MEMORY_GROWTH; WebGPU selects -sJSPI.
                  • "The map lives on a worker. Always." Atomics.wait throws on the browser main thread, and MapLibre blocks (waitForEmpty(), teardown joins) ffi#37.
                  • Cross-origin isolation is mandatory for threads (COOP/COEP in run-browser-test.mjs:226). A map library cannot impose response headers on its host page [inferred].
                  • JSPI, not Asyncify: Asyncify "aborts outright over a module built with native exception handling"; JSPI "roughly halves" the module but means Chrome 137+/Firefox 139+ only. Upstream's default is still -sASYNCIFY=1, configurable since #4451.
                  • emscripten_fetch completes on the issuing thread's JS event loop, which MapLibre threads never return to, so the FFI runs a TransportThread http_file_source.cpp:200. No ambient cache in the browser, yet sqlite is linked.
                  • Distribution: core/v0.202610.0 ships emscripten archives (10.2 MB tarballs) "only usable with a matching emsdk version".

                  Risk register for "one core on the web"
                  Severity ratings are [inferred]

                  The design implication [inferred]: the architecture ports; the engine's assumptions do not. MapLibre Native assumes blocking threads with shared memory, synchronous GPU calls and a fat compiled-in platform layer. A core that is a good web citizen needs share-nothing workers, async-tolerant GPU submission, and host services (fetch, image decode, Intl, glyph rasterization) delegated to the browser. GL JS already has the only embeddable split. For Compose specifically, 3 MB gz is not a deal-breaker next to 3.3 MB gz of Skia; for GL JS's audience it is. The Orbis plan does not try to move Native to the web. It sketches a separate, third engine whose Rust core builds for plain wasm32-unknown-unknown, with no Emscripten, COOP/COEP or JSPI (its D2), and targets the web and native from its first milestone (its D3) within a 450 KB br initial budget; GL JS stays the lighter choice for web pages.

                  Lessons

                  Keep, change, avoid

                  The downstream projects have already run most of the experiments a new engine would need. Compose ran "one engine, thin hosts". The FFI ran "C ABI as the only boundary". maplibre-rs ran "start from the renderer". Mapbox ran "share the tests, not the code".

                  Every item is a recommendation, so it is [inferred], resting on the verified evidence linked under it. The Orbis plan, for a separate third engine that owes Native and GL JS no compatibility, turns these into its own decisions. Its D18 borrows the FFI's C ABI conventions for a new orb_ ABI and shares one binding-emitter repository with the FFI. The FFI itself stays a separate project, still Hosted tier with 30 stars, 26 patches and a draft execution model.
