Parity atlas

Two engines, one spec, many copies

MapLibre Native and MapLibre GL JS descend from the same Mapbox code, render the same style JSON, and are tested against fixtures copied from the same ancestor. Almost nothing between them is shared at build time any more. This page maps where they are duplicated, where they disagree, and how long it takes a feature to cross from one to the other.

Native consumed GL JS as a git submodule (shaders, the style-spec reference, the integration tests) until native#938 removed it on 2023-03-25. Since then every shader, test and spec change has been ported by hand, in whichever direction someone was paid or motivated to port it. The style-spec repo itself was carved out of gl-js on 2023-02-19; the TypeScript package it ships is GL JS's expression engine and validator, while Native carries its own C++ engine and a hand-patched copy of v8.json.

The result is measurable. Across 67,872 paired non-test lines (17 pipeline stages, 70+ file pairs) the LOC-weighted token-sequence similarity between the engines is 6.8%, against a noise floor of about 1% for unrelated files. 203 of the spec's 535 sdk-support rows are JS-only, but the tables are stale in both directions: about 166 native rows and 3 JS rows describe code that has already shipped or merged. Of 1,250 render tests the two repos share by path, 1,186 are semantically identical and live as two hand-synced copies.

Lineage 17 stages · 87 pairs

Same concepts, rewritten bodies

The engines still share names for leaf helpers and the shape of the symbol pipeline. Orchestration (threads, tiles, resources, rendering) was re-architected independently on each side and shares essentially nothing.

The lineage measurement pairs files by role, not name: TilePyramid with TileManager, GeometryTileWorker with WorkerTile, RenderCircleLayer+tweaker with draw_circle+program. It strips comments and string literals and computes three scores per pair:

  • defC: shared defined function names ÷ the smaller side's count. How much of the smaller API surface reappears on the other side; the best single lineage indicator.
  • idJ: Jaccard overlap of identifier sets.
  • seq: difflib ratio over the ordered identifier streams. High only for line-by-line transliterations.

Four unrelated control pairs (offline_database vs marker, annotation_manager vs popup, pmtiles_file_source vs hash, action_journal vs handler_manager) score 0.00 / 0.01 / 0.01: that is the noise floor. Per-pair numbers carry ±0.05 because regex extraction misses some template-heavy C++.

Lineage survives in leaves: symbol geometry (quads seq 0.55, 88% of names shared), check_max_angle (seq 0.64), intersection_tests (92% of names), GLSL shaders (seq 0.49), the distance/within expressions (62%), LineAtlas (seq 0.42). Render prep scores 2%, map/camera 3%, tile parse 2%, resource loading 0%, events 0%. The parts that cause the most bugs are the parts each side re-architected: Native's actors (2016), immutable impls (2017) and drawables (2023); GL JS's projection seams (2024) and Graphics Modernization (2026).

Knowledge flows one way in comments: native src/mln has about 16 hand-written references to gl-js files or behaviour; GL JS src has one reference to native (src/data/load_geometry.ts:25, “mapbox-gl-native uses integers”). 14 of roughly 185 human committers in the last year committed to both repos. How each engine is built is on the anatomy page.

sdk-support 535 rows · 30 groups

What v8.json says each SDK supports

Every property, expression and sub-feature in the spec carries an sdk-support block with a version or an issue link for js, android and ios. Extracted row by row from src/reference/v8.json at 55f1c29b, with the rows the research found to be wrong flagged in place.

A row is a (path, feature) pair, for example layout_symbol.text-variable-anchor-offset × “data-driven styling”. As written, the partition is 318 supported on all three · 203 JS-only · 4 native-only · 10 nowhere. One JS cell holds the literal value "supported" rather than a version or an issue link; counting it as unsupported gives a wrong 204. 155 of the 203 JS-only rows are global-state, and one native issue, native#3302, accounts for 312 platform cells.

The spec had a macos column until spec#654 removed it on 2024-05-06, when 289 rows carried a value. The matrix shows it as a historical column read from cf623c0c, the commit before #654. Linux, Windows, Qt, Node and OHOS have never had columns (spec#391, open since 2023-10-20).

What enforces the table. src/index.test.ts:28-45 requires every layer property and expression to have a “basic functionality” row, and src/expression/expression.test.ts:23 asserts that the TS expression registry equals the set of expressions with a truthy js value. Nothing checks the android or ios values against code. JS support is therefore defined as “implemented in this package”; native support is whatever someone last typed.

15 root-level and projection entries have no sdk-support block at all, including $root.sky, $root.terrain and $root.projection, so the spec does not record that Native ignores them parser.cpp:43.

The fork 9,357 → 8,375 lines

A hand-patched v8.json and three code generators

Native does not consume the spec package. It carries an 8,375-line copy (upstream: 9,357) that feature PRs edit by hand, mutates it with a script, and feeds it to three separate generators.

Native's package.json depends on @maplibre/maplibre-gl-style-spec ^24.7.0 while upstream is 26.4.x. Its only spec script is copy-style-spec. In practice the copy is hand-edited in feature PRs: the last five commits touching it are native#4516 (global-state; 576 lines added to the file), native#4604, native#4343, native#3965 and #3205 (whitespace). A draft resync, native#4523 (+1,770), is open, as is “Patch style spec based on sdk-support” (native#2768).

Native has no validator: parser.cpp (465 LOC) has 24 Log::Warning(Event::ParseStyle, …) call sites, and invalid layers or properties are dropped with a log line. A style that validates in GL JS can partially render on mobile with no error.

About 30k LOC of checked-in generated code across 98 native files, plus the Darwin output generated at build time; 21 EJS templates; 5,039 LOC of templates and generators. Generated headers still say Edit scripts/generate-style-code.js, then run make style-code; the script is .mjs and there is no Makefile. Every native property is a distinct C++ type, so adding an enum property also needs a hand-added template instantiation in function.cpp (1,033 LOC).

Downstream, at least 7 style-property codegens read the same v8.json. maplibre-native-ffi has none: it exposes generic name + JSON setters (97 MLN_API functions in style.h), a working proof that per-property generated SDK surfaces are optional.

Duplication ledger one tick = one implementation

N implementations of everything

The same concern implemented again and again: inside Native per platform and per GPU backend, across Native and GL JS, and once more in every downstream SDK.

Inside Native, the platform seam is link-time, not an interface: core declares util::RunLoop, HTTPFileSource, decodeImage, LocalGlyphRasterizer, Collator, NumberFormat, threads and logging, and each platform chooses which .cpp files to compile, in CMake and again in Bazel. Picking the wrong file compiles cleanly and fails silently: maplibre-native-ffi's Apple build compiled the Qt bidi placeholder and shipped Arabic and Hebrew labels unjoined (ffi#788); number-format falls back to std::to_string (1234.500000 for de-DE EUR) when MBGL_USE_BUILTIN_ICU is set (ffi#797).

Per GPU backend, the “shared” glue is copy-pasted: drawable_builder.cpp is 88% line-identical between Metal and Vulkan, the buffer resources 85%, layer_group.cpp 69–78% across Metal/Vulkan/WebGPU. Shaders are hand-written four times; every UBO struct is declared once in C++ and again per dialect (GlobalPaintParamsUBO is copied into 8 WGSL headers). Platforms 259,225 platform lines : 166,355 core

One core, nine hosts, different behaviour

The same C++ core sits behind Android, iOS, macOS, Qt, Node, GLFW/Linux, Windows and OpenHarmony, and GL JS is the ninth host. Which services, threads, backends and SDK features each one gets is decided per platform.

There is more platform code than core: 259,225 lines across 1,554 files in platform/*, against 166,355 lines in src/mln + include/mln (≈1.56 : 1). Most of that weight is SDK UX (map views, gestures, annotations, location, style wrappers), not engine integration: the Darwin C++ glue is only 1,356 lines under a ~47k-line ObjC SDK.

Threading differs per host, and behaviour diverges with it: native#2828, Android queryRenderedFeatures(layerIds=[]) ignores the empty array while iOS and GL JS filter to nothing (found by flutter-maplibre-gl). Versions are independent: Android 13.x, iOS 6.x (7.0.0 pre-releases in flight), Node 6.5.0-pre.1, core core-<sha> builds. The anatomy page covers how each host is built.

Conformance 89 MB + 79 MB of fixtures

One fixture set, two hand-synced copies

Render, query and expression tests are language-neutral JSON plus PNGs, and both engines run nearly the same ones. They are copied by hand between two repos, with per-engine ignore lists and per-platform expectations.

Native ran the GL JS copies via submodule until native#938, whose stated reasons were “Native and JS have different source code, so they should have separated render tests” and “JS submodule is outdated”. Since then the suites drift. Of the 1,250 shared render tests, 840 have byte-identical style.json, 346 differ only in formatting or key order and 64 differ semantically, so 1,186 are semantically identical. Traffic goes both ways now: gl-js#8388 copied 39,932 lines of color-relief and terrain tests from native, and the native globe PR native#4533 adds 22,678 lines of render tests from GL JS.

The render-test operation protocol differs: GL JS's harness dispatches any Map method name, so the test format is GL JS's public method namespace; native's render-test/parser.cpp hard-codes about 41 operation names, some with no GL JS equivalent (probeMemory, setTileLodScale, panGesture).

Nondeterminism is handled in opposite ways. Native keeps 12 ignore files (255 entries) plus alternate expectation PNGs per platform. GL JS keeps no ignore list; it accepts multiple expected images instead: 1,958 PNGs for 1,718 tests, about 50 ad-hoc suffix conventions (expected-win-flaky9.png, expected-half-float.png…), worst case 14 variants.

Archaeology: 83 native ignore entries mention mapbox-gl-native; in GL JS, 114 of 117 regression tests are named after Mapbox issues. Tracking has stalled: native#2445 “Render Test Parity” and native#2373 “Render Test Parity Tool” (2024) are both open with 0 comments.

Text HarfBuzz vs Intl.Segmenter

The same label, shaped two ways

Both engines run the Mapbox symbol pipeline, but text shaping split in 2025–26 into two different architectures, and placement scheduling diverged years earlier. The same style gives different glyphs, wrapping and direction per platform.

Native added HarfBuzz + FreeType in native#3611 (merged 2025-07-29, +27,006/−151), on by default but only for runs covered by root font-faces. Those runs skip bidi and line breaking, are always shaped LTR (hb_buffer_set_direction(buffer, HB_DIRECTION_LTR)), and are shaped and rasterised on the render thread. RTL Kurdish comes out reversed (native#4513, open).

GL JS (gl-js#8237, gl-js#8343, gl-js#8488, September 2026) does not shape. It segments text into grapheme clusters with Intl.Segmenter, lets the browser draw each cluster on a canvas via TinySDF, uses bidi-js and a pure-TS Arabic joiner, and deprecates the ICU-in-WASM RTL plugin.

Placement: GL JS has PauseablePlacement with a 2 ms/frame budget, skips re-placement when inputs are unchanged (gl-js#8208) and rewrites opacity buffers only for changed buckets (gl-js#8434). Native places every layer synchronously on the render thread whenever placement goes stale: period max(300 ms, fade) × (1 − zoomAdjustment), 30 ms when new buckets arrive on an untilted view, every frame when transitions are off. It also carries 28 canary guard words per SymbolInstance, which cost 37% of app CPU in one profile (native#4749).

Feature lag

How long a feature takes to cross

Timelines for features that landed in one engine and then the other, from proposal to the spec, each engine's merge and release, and the spec-table update. Lag runs both ways and follows funding.

JS-first features usually take 5–18 months to reach a native release; the big GPU features (terrain, globe, sky) take years or have not arrived. global-state took 525 days from spec merge to native merge and is still unreleased on a stable line; interpolate-hcl/lab took about eight years (GL JS 0.49.0, 2018 → native#4668).

Native-first features happen when a company funds native: HarfBuzz/font-faces (@stefankarschti), MLT (@TimSylvester), rounded corners (@alexcristici) framing inferred. distance was a Mapbox-era native-first expression that GL JS got about 3.4 years later.

The spec process can be the bottleneck: semiliteral's spec PR (spec#951) sat 19 months, then reached GL JS and native iOS within weeks. The projection proposal spec#568 has been open 2.5 years although globe shipped in GL JS 5.0. Of 61 proposal issues in the spec repo, 40 are open with a median age of 491 days.

Lag compounds downstream: feature-state existed in the native core before the December 2020 fork, reached the Android SDK in July 2026 and iOS in September 2026, and flutter-maplibre-gl (pinned to iOS 6.28.0) still documents it as unsupported on iOS.

Porting direction 2014 → 2026

Converging by copying

Porting stopped at the fork and restarted in 2026, in both directions, without sharing code. Each engine is adopting the other's architecture by transliterating it.

Commit messages mentioning “port … gl-js” in native: 2014: 4, 2015: 9, 2016: 17, 2017: 15, 2018: 18, 2019: 6, 2020: 5, then 2026: 1. Porting resumed in 2026 in PR bodies and under the js-parity label: distance-LOD native#4057, CJK fixes native#4553 and native#4566, global-state native#4516, and the globe PR native#4533 (“GL JS's math is the spec and GL JS's render tests are the oracle”).

In the other direction, GL JS's Graphics Modernization (gl-js#7640) ports Native's drawables, tweakers and UBOs (gl-js#4511, gl-js#8556); its WebGPU PoC gl-js#7411 was “an early port of the drawables-based WebGPU backend from Native”; Camera State Consolidation (gl-js#8694) moves GL JS to native's one-writer camera model. End state if nothing changes: two codebases with the same architecture in two languages, plus 5–6 shader dialect sets inferred. A search of the org found no issue proposing a single shared engine. The proposal page does not propose merging these two; it sketches a separate, third engine that borrows from both and leaves them to evolve on their own roadmaps.

Downstream cost RN · Flutter · Compose

Every cross-platform SDK stitches two or three engines

React Native, Flutter and Compose wrap the Android SDK, the iOS SDK and GL JS behind one API. Each difference upstream becomes an UnsupportedError, an expect/actual split, a re-implementation or a parity script downstream.

maplibre-compose dropped the official Android and iOS SDKs in August 2026 and moved Android, iOS, macOS and JVM desktop onto maplibre-native-ffi (compose#834, compose#844, compose#985). Before, each of the 11 layer types had its own actual file per platform: about 754 actual declarations. Now about 260, and one maplibreNativeMain source set (6,883 LOC) serves four platforms. The stated motive (compose#572): “eliminate API differences between the different SDKs”.

Compose still has two engines (native via FFI, web via GL JS), so divergence is part of its public API shape: expect option classes, features left out of a source set, reads that return empty and writes that throw UnsupportedOperationException. It keeps two living limitation trackers (compose#1639 Native, compose#1718 GL JS), 30 issues labelled blocked-upstream, and its own parity machinery: ci/style_spec_parity.py (782 LOC) reads sdk-support per engine and filters native-unsupported writes “so a write cannot refuse the whole layer”.

flutter-maplibre-gl wraps the Android SDK 13.5.0, the iOS SDK 6.28.0 and GL JS, through a god class per platform (MapLibreMapController.java 149 KB, .swift 125 KB). setProjection(), setTerrain(), setSky() and setGlobalStateProperty() “throw an UnsupportedError on Android and iOS”. Discussion flutter#907: “Every feature … written three times: Dart, Kotlin, Swift”.

maplibre-react-native wraps Android 13.6.1 and iOS 6.31.0 with no web, re-implements markers, callouts, location, offline and snapshots on both platforms, and tracks upstream gaps (rn#562). Downstream bugs bubble up as divergence reports: native#2828 (Flutter), native#3818 / native#3223 (React Native), native#3777 (Compose font clash). The ecosystem map is on the field notes page.

Takeaways

Parity is a property of tests, not tables

Every layer of today's parity system is manual: hand-edited sdk-support, a hand-edited spec copy, two hand-synced test corpora, a parity tool issue with no comments, and downstream parity scripts. The truth is “what passes the shared tests on each engine”, and nothing computes it.

  1. One conformance corpus, consumed by both engines. 1,186 of 1,250 shared render tests are already semantically identical and 1,120 share at least one byte-identical expected PNG. Each engine keeps only an ignore manifest with linked issues.
  2. Generate sdk-support from results. Each build emits a capabilities manifest; spec CI computes the table, with columns for every host (Linux, Windows, Qt, Node, OHOS, web; spec#391) and global-state as one capability instead of 156 rows inferred design.
  3. Delete Native's spec fork. Consume the spec package directly; one generator emits core property tables, the C ABI and SDK typings. The FFI already proves generic JSON setters work.
  4. Shared semantics for host-dependent operators. number-format (5 backends) and collator (4) need one implementation or a documented host-service contract with its own tests inferred.

These are changes Native, GL JS and the spec can make on their own. The Orbis plan sketches a separate, opt-in third engine that needs none of them: it mirrors the shared fixtures read-only and offers a merged, platform-tagged corpus to both engines as an invitation, never a gate (its D21).
