01 · The big picture

Where the lines are

Native is a 166k-line C++ core wrapped in 259k lines of platform shells, and the single biggest thing in its public header tree is shader text. GL JS is a 71k-line TypeScript package with almost as much unit-test code, and one file, map.ts, is 6.6% of it.

Native

The core splits into four roughly equal masses: the style system (35k lines, half of it generated layer classes and the expression engine), the renderer (25k), the shaders (29k inside core plus 4k of GLSL source at the repo root), and everything else. The four GPU backends add 25.6k lines of C++ glue; summed per backend with their shader sets they are 14.5k (GL), 11.4k (Metal), 14.4k (Vulkan) and 12.3k (WebGPU).

Half of include/mln is not API: include/mln/shaders is 24,313 of its 50,058 lines. The platform directories outweigh the core 1.56 : 1, and Android alone (143k lines, 22k of it JNI C++) is 86% the size of the whole core. The Apple C++ glue that binds the engine is 1,356 lines; the other ~82k Apple lines (darwin + ios + macos, including sample apps and tests) are SDK and app code.

Not in the treemap: test/ 37,698 lines of C++ sources; metrics/ 10,904 files and 202 MB of expected images; vendor/ 800 MB across 38 submodules, plus a checked-in SQLite amalgamation of 269,313 lines.

GL JS

324 tracked non-test .ts files hold 70,918 lines (tokei: 46,413 code, 16,304 comment, 8,212 blank), plus 71 GLSL files (3,739 lines) and 86 build-generated *.g.ts files (2,410 lines) that are not in git. Unit tests add 217 files and 60,929 lines, a test-to-source ratio of 0.86.

ui/ is the largest directory (15,132 lines) because it holds Map (4,710), Camera, HandlerManager with 20 handler files, markers, popups and nine controls. The data and symbol cores are still mostly Mapbox code: by git blame -w -C against a 2020-12-09 cutoff, 58% of data/ and 48% of symbol/ predate the fork, against 10% of geo/. Across src/, 36% of lines survive from v1.13 (a lower bound).

At the type level the code is nearly one cycle: counting import type, 254 of ~410 files form a single strongly connected component. The source is typechecked with "strict": false; only the emitted maplibre-gl.d.ts is strict.

02 · Architecture

The layers of each engine

Native is a stack of modules with three hard seams: an immutable style snapshot between map and renderer, a compile-time GPU backend under the renderer, and link-time platform services under everything. GL JS is a main-thread orchestrator, a worker-side tile pipeline and an immediate-mode WebGL2 renderer. Select a module to see what it owns, which thread runs it, and where it hurts.

Native

Read the stack as the life of a state change. The app calls the API on the map thread; Style mutates copy-on-write Immutable<Impl> objects; Map::Impl::onUpdate() packages camera and every immutable layer, source and image into an UpdateParameters snapshot and hands it to a platform-provided RendererFrontend, which decides when and on which thread to call Renderer::render.

On the render thread, createRenderTree diffs the snapshot by pointer identity, re-evaluates what changed, updates every TilePyramid (which fires tile requests), runs placement, then turns buckets into retained drawables. Everything platform-specific is chosen by which .cpp files the build compiles; the only runtime platform seam is FileSourceManager::registerFileSourceFactory.

GL JS

A main-thread orchestrator (Map → Style → one TileManager per source → Painter) owns the camera, the style model, tile selection, symbol placement, GPU upload and every draw call. A Web Worker pool decodes tiles and lays them out into vertex and index arrays (Worker → WorkerSource → WorkerTile → Bucket).

The renderer is immediate-mode WebGL2: Painter and webgl/draw/draw_*.ts re-issue every draw call every frame, and nothing persists between frames except the GL state cache and per-segment VAOs. Map (4,710 lines) and Style (2,201) are the two god objects. map.ts:592style.ts:204

03 · Concurrency

Fourteen threads, or two

A Native map runs about fourteen threads before counting the HTTP stack, but nearly all per-frame CPU work lands on one of them, and which one depends on the platform. GL JS runs on the page's main thread plus a page-global worker pool that, on Chrome and Firefox, has exactly one worker.

Native

The map thread is whoever constructs mln::Map; it owns the API, camera, style mutation, the synchronous style-JSON parse and every UpdateParameters. The render thread does style diffing, evaluation, tile requests, glyph PBF parsing, HarfBuzz shaping, placement, drawable building, upload, encode and present. Everything else is a 4-thread process-wide worker pool, up to ten sequenced schedulers, and seven file-source threads per distinct ResourceOptions.

On iOS and macOS map and render are both the main thread (CADisplayLink → drawInMTKView: → renderSync), so GPU encoding shares main with UIKit. On Android the map lives on the UI thread's ALooper and the renderer on the GL thread; queries block the UI thread on a std::future. Background work has no priority, and ARCHITECTURE.md's "four per Style object" is wrong: the pool is shared by all maps.

GL JS

The pool size is one line, unchanged since 2023 #2354worker_pool.ts:59: workerCount = isSafari ? max(min(floor(hardwareConcurrency/2), 3), 1) : 1. The worker decodes MVT/MLT, runs geojson-vt, evaluates layout and filters, triangulates, subdivides for the globe and lays out symbols. The main thread does everything else: camera, style evaluation, tile selection, glyph SDF rasterization, raster decode, custom protocol handlers, placement, line-label reprojection, queries, upload and every draw call.

Messages cross through Actor, a promise RPC over postMessage with 23 message types and a hand-rolled serializer (84 register() sites) that moves bucket arrays zero-copy. In the best whole-session profile in the notes, the main thread was busy 2,089 ms against the worker's 609 ms. #8426

    04 · Data flow

    Follow an uncached tile

    On Android one vector tile that is not in the cache crosses threads sixteen times between the moment TilePyramid decides it needs it and the frame that draws it. In GL JS the same tile crosses the main/worker boundary four times, but its expensive moments happen on the main thread.

    Native · 16 hops

    The verified per-hop trace (it supersedes an earlier "about 12" estimate) assumes Android with OkHttp, a tile absent from the ambient cache, and glyphs and sprite already loaded. Four phases: a cache probe (CacheOnly request, miss); a second, separate NetworkOnly request through the same waterfall; worker parse and layout, interrupted by a round trip to the render thread for glyphs and images; and frame scheduling, where the render thread asks the map thread to build a whole new snapshot just to say "redraw".

    iOS/macOS: 14 (map = render). Linux GLFW + curl: 12. An uncached glyph range adds a full second chain of 10. Side messages (the cache write 9b, the worker's self-sent coalesced 11b) are drawn dashed and not counted.

    GL JS · 4 hops

    A VectorTileSource with an http(s) URL on Chrome (one worker), glyphs and sprite loaded once but this tile needing a new glyph range. Watch three things. The worker asks main for glyphs, images and dashes mid-parse, and CJK or cluster glyphs are rasterized on main while it waits. The result is not uploaded on arrival; main stores it and fires data, and upload happens inside the next Painter.render. And the raw tile bytes come back too, copied, so queries and feature-state can decode them again on main.

    A tile URL whose protocol was registered with addProtocol only on the page (PMTiles, for example) inserts three steps and two more hops: the worker bounces the fetch to main through getResource. The 4/6 hop counts are derived from the verified sequence.

    05 · Rendering

    Anatomy of a frame

    Native renders through retained drawables refreshed every frame by per-layer tweakers, behind four GPU backends chosen at compile time. GL JS is an immediate-mode WebGL2 renderer that re-issues every draw call each frame, and since May 2026 it has been turning itself, one PR at a time, into a port of Native's design.

    Native

    Renderer::Impl::render runs a fixed sequence: upload pass, updateLayers (every RenderLayer::update builds or refreshes drawables), queued changes, a second upload pass where every layer group runs its tweakers to fill UBOs, render-target passes, then the main pass: opaque groups front to back for early-Z, translucent back to front, debug, present.

    What runs every frame regardless of change: cross-tile symbol indexing, CPU line-label reprojection, RenderLayer::update for every layer, every tweaker for every drawable (getTileMatrix: 22 call sites, no cache), a stencil mask per tile per layer group, and a full re-encode. There is no "nothing changed, replay" path.

    The legacy renderer was deleted on 2025-04-15 on the basis of "similar or better performance" #3384. The only multi-device A/B (17 Android devices, Nov 2024) shows drawables-GL at 0.86× legacy throughput in CPU-bound async mode and 0.95× in sync mode #2787; #3438 (Qt/OpenGL on desktop, 69.9 → 11.4 fps) is still open #3438.

    GL JS

    Map._render updates style, sources, terrain and placement, then Painter.render builds a fresh FrameRenderContext, writes the frame UBO, uploads pending tile data and walks the layers three times: offscreen, opaque top to bottom, translucent bottom to top. Depth is a layer-order buffer (glDepthRange(d, d) per sublayer), and stencil holds 8 bits of per-frame tile IDs.

    Programs are keyed on name × data-driven config × projection × terrain × overdraw and compile synchronously on first use #8338. Program.draw takes 19 positional arguments. On a fast laptop the walk is cheap: about 1.7 ms of CPU and 449.6 drawElements per frame for Liberty over Tokyo at z15 #8474.

    The Graphics Modernization series #7640 is moving shared state into std140 UBOs and an explicit FrameRenderContext, aiming at retained drawables "following maplibre-native's drawable / tweaker design", then instancing, then a lazily loaded WebGPU backend.

    06 · Style pipeline

    From style JSON to uniforms

    Both engines parse the same spec through two independent code generators into two property systems. Native's distinguishing trick is immutable snapshots compared by pointer; GL JS batches setter calls between frames and diffs whole styles with the style-spec's diff().

    Native

    Parser::parse (rapidjson, 465 lines) reads sources, layers, light, state, font-faces and camera keys, but not sky, projection, terrain or metadata, though its vendored spec defines them: a globe style renders flat with no warning. There is no validator, only 24 kinds of Log::Warning. parser.cpp:43

    A generated setter copies the entire layer Impl, copy-on-writes the collection, and publishes a whole new UpdateParameters. Nothing batches: N setters make N snapshots. Generated set*Transition setters forget to notify at all #4676#4677#4678. The expression engine is a second complete implementation: 10,623 lines of C++ against 7,964 of TypeScript, running 363 of the spec's 577 fixtures.

    GL JS

    _load validates with the style-spec validator and creates layers on the workers first, "so that expensive style processing can happen in parallel". setStyle(next) runs the spec's diff() and maps its commands onto the public setters: 23 case branches, 18 applied and 5 camera commands ignored; anything unknown throws "Unimplemented" and the whole style is rebuilt. style.ts:897

    Setters only mark dirty sets; Style.update flushes them from Map._render. A paint change costs new uniforms next frame. A layout or filter change, or a paint change that flips constant ↔ data-driven, re-parses every tile of that source on the worker.

      07 · Text & symbols

      One symbol engine, written twice, split on shaping

      Both engines run the same Mapbox-era symbol pipeline, function for function. In 2025–26 they split on the hardest part: Native shapes some text with HarfBuzz on the render thread, and GL JS lets the browser draw whole grapheme clusters on the main thread.

      About 9.6k lines of C++ (src/mln/text + layout/symbol*) face 7.75k lines of TypeScript in src/symbol. Of 279 Native and 247 GL JS function names in the area, 91 are shared, so the algorithms map one to one even though the code no longer diffs line by line: leaf geometry like quads is still a near-transliteration, while shaping, placement and layout have drifted structurally.

      Native added HarfBuzz + FreeType in July 2025 #3611 for runs covered by the root font-faces property. Those runs skip bidi and line breaking and are shaped as LTR, which is why RTL Kurdish comes out reversed #4513; shaping and FreeType rasterization run in GeometryTile::onGlyphsAvailable on the render thread geometry_tile.cpp:395. GL JS does not shape: it segments text into grapheme clusters with Intl.Segmenter and lets the browser's own text engine draw each cluster through TinySDF, with a pure-TS Arabic joiner and bidi-js replacing the RTL plugin #8237#8343. The same style now gives different glyph sets, wrapping and direction on each platform.

      Placement diverges too. GL JS runs PauseablePlacement with a 2 ms per-frame budget and skips re-placement when inputs are unchanged; Native places every symbol layer synchronously on the render thread whenever placement goes stale, and every SymbolInstance carries 28 canary words that cost 37% of app CPU in one iOS profile #4749.

      The shared pipeline (both engines)

      Neither engine kerns or applies OpenType features on the PBF glyph path; advance is per codepoint. Server glyph PBFs cover 256 codepoints each, SDF radius 8, rendered at 24 px with a 3 px border.

      08 · Projection

      Mercator all the way down

      Native has no projection seam: a static Spherical Mercator utility from 2015, a camera stored in Mercator pixels, and one 4×4 matrix handed to shaders. GL JS has had a globe since v5, built as Web Mercator tile geometry bent onto a unit sphere in the vertex shader.

      Native

      Three things are named "projection" and none is an abstraction: mln::Projection (static functions, 2015), ProjectionMode (axonometric skew, 2019) and MapProjection (a detached Transform, 2022). TransformState stores the centre as Mercator pixels; matrixFor(tileID) is an affine; each tweaker's getTileMatrix hands one mat4 per drawable to shaders that compute u_matrix * pos, and that matrix is the entire projection contract.

      The globe PR #4533 is open at +43,144 / −1,361 across 645 files and 130 commits, mapping GL JS's five seams onto one ProjectionBase and adding projectTile preludes to all four shader dialects. Pre-releases shipped on 2026-10-08 from commits not on main. Terrain is a separate open PR #4190.

      GL JS

      createProjectionFromName returns a triple {Projection, ITransform, ICameraHelper}. 'globe' is sugar for ['interpolate', ['linear'], ['zoom'], 11, 'vertical-perspective', 12, 'mercator']: a zoom-interpolated blend of two projections. The worker subdivides geometry along a Mercator-aligned grid; each vertex goes tile → Mercator → unit sphere in the prelude, then blends back to the per-tile Mercator matrix as the transition falls. projection_factory.ts:42

      The abstraction covers vertex position only: 24 of 71 GLSL files still carry #ifdef GLOBE, and switching projection reloads every TileManager because subdivision happens at parse time. A planar custom-CRS addProjection is in review #8723, answering the most-reacted open issue #168.

      09 · Platforms

      Nine shells around one core, and a browser

      Every Native platform supplies the same five things to the core: an event loop, an HTTP stack, an image decoder, a renderer frontend and a backend. It supplies them by compiling different .cpp files rather than by implementing an interface, and then rebuilds most user-facing features on top in its own language. GL JS has exactly one platform, and its hard problems are browsers and bundlers.

      The services matrix has four RunLoops, five HTTPFileSource implementations plus Node's JS-callback source, five image-decoder stacks in six files, five loggers, four local glyph rasterizers and two SQLite providers, each chosen in platform/*/*.cmake and again in Bazel. Binding styles differ sharply: Android goes through JNI with 488 Java native methods plus 89 Kotlin external fun; Darwin calls C++ directly from ObjC++ (MLNMapView.mm is 7,919 lines); Node uses NAN. For about 17 user-facing features, Android and Apple each carry their own implementation, roughly 30 parallel implementations in-tree inferred before Compose, Flutter, React Native and SwiftUI wrappers wrap them again. Versions are independent: Android 13.6.1, iOS 6.31.0, Node 6.5.0-pre.1.

      10 · Build & developer experience

      Nine build systems, or one rolldown config

      The same C++ core is built by CMake, by Bazel and through Gradle, with Xcode projects generated two ways and npm and pnpm lockfiles for one package.json; CI runs about 121 jobs and takes nearly two hours per platform. GL JS is one rolldown build of three ES modules, 1,718 software-GL render tests in twelve CI jobs, and a release every five to six days.

      Native

      CMake (83 files, 33 configure presets) is the only path for Android's NDK, Qt, vcpkg, Node, OHOS and Vulkan. Bazel 8.6.0 is primary for iOS and macOS: reproducible XCFrameworks, the generated Xcode project and the Darwin style codegen at build time. Gradle 9.5.1 drives CMake per ABI × flavor. Every vendored dependency is wired twice (1,598 lines of vendor/*.cmake, 734 of vendor/BUILD.bazel). Configuration is compile-time: exactly one of MLN_WITH_OPENGL|EGL|VULKAN|METAL|WEBGPU, so Android's multiBackend flavor builds the core twice (~31–33 MB AAR vs ~15 MB).

      31 workflow files, 71 job definitions, ~121 jobs after matrix expansion; p50 wall time android-ci 105 min, ios-ci 115, linux-ci 111. Windows CI has been off since July 2025 #3670. vendor/ is 800 MB across 38 submodules; the git pack is 5.80 GiB.

      GL JS

      npm run codegen runs four generators; rolldown.config.ts (41 lines) has two entry points, maplibre-gl and maplibre-gl-worker. The v6 tooling overhaul replaced Rollup with Rolldown, dts-bundle-generator with oxc isolated declarations and tsc with tsgo. The pre-v6 bundle stringified its own module factories into a Blob to start the worker, which is why a separate CSP build existed for years; v6 is ESM-only and finds its worker from import.meta.url, which bundlers break.

      Render tests run in headless Chrome on SwiftShader, ubuntu + windows × 6 splits; main-branch CI typically finishes in about 5 minutes. GL JS keeps no ignore list: 146 tests accept more than one expected image. 1,250 render-test paths exist in both repos, copied by hand.

        11 · Extensibility

        Seven custom-content mechanisms in Native; the inverse in GL JS

        Native has accumulated seven overlapping mechanisms for custom content, from Mapbox-era annotations to a C plugin ABI merged in September 2026, and none has been retired. Only layers are pluggable; sources, tile formats, URL schemes and projections are closed. GL JS is the mirror image: pluggable sources and protocols, no style-integrated layer-type plugins.

        Native

        The C ABI #4612 is the most carefully versioned API in the repo: every struct starts with uint32_t struct_size, strings are {data, size}, descriptors declare min/max host ABI and are deep-copied, status codes replace exceptions. The host owns sources, tile scheduling, drawables, uploads and transitions; plugins own layout callbacks (on workers) and shaders (GLSL or MSL; no WebGPU path). To get four real plugins working, maplibre-plugins carries six ABI patches (~3.3k lines). It is "unstable v1".

        RenderSource::create is a closed switch; TileDataFormat has one value. A C++ CustomDrawableLayer lived from 2023 until it was removed on 2026-09-10 "in preparation of the C API" #4611.

        GL JS

        Six real seams, all on the main thread except an "experimental, can break at any point" door into the worker (importScriptInWorkers). Custom layers get the raw WebGL2RenderingContext, which GM keeps "as-is" and which is the main WebGPU compatibility hazard #4511. addProtocol writes a page-global, per-realm registry. src/index.ts exports 222 names including Painter, Tile, Bucket, Actor and Dispatcher: the extension story is, in effect, "here are our internals" inferred.

        No computed-source API runs in the worker, so maplibre-contour encodes isolines as MVT for the MapLibre worker to decode again inferred. Plugin authors who target both engines write two implementations.
