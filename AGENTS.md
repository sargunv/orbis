# Orbis

An experimental, ground-up Rust renderer for the MapLibre v8 style spec,
built and steered entirely by AI agents. One core renders on wgpu: in the
browser through wasm and WebGPU, and natively through Vulkan, Metal and
D3D12.

Its aim is to be a modern, next generation renderer able to develop quickly,
support new features, and perform better than the existing renderers
(maplibre-native, maplibre-gl-js, mln-rs) on download size, load time,
tile processing and rendering speed, in  2D and 3D, while drawing v8
styles correctly. Scope is the v8 spec plus what it could reasonably grow
into: projections, coordinate reference systems and tile matrix sets. Features
beyond that don't belong. New style keys, values and expressions beyond the
approved spec (style-spec proposals, `orbis:` metadata, coordinate reference
systems and tile matrix sets) sit behind the preview switch (#134), off
unless a map opts in, so a style never depends on them by accident: a new
one is a `Preview` in `orb-style`, gated where its input parses. Wiring
that adds no new syntax is always on: transitions on anything practical,
and inputs a property's evaluation phase can honour beyond the spec (its
table entry's `extends`). Where GL JS or Native would reject such a style,
for example a data-driven expression on a property the spec keeps
constant, Orbis draws it and warns once that it isn't portable.
`docs/style-support.md`, generated by `cargo xtask support`, lists the
previews and what each property accepts. The C, Kotlin and Swift bindings
(`orb-capi`, Diplomat) will be replaced by
[maplibre-native-ffi](https://github.com/maplibre/maplibre-native-ffi)'s C
API, so keep them building and don't grow them.

## This is your project

While you work here, you own it. The roadmap, issue triage, bugs, features,
performance, demos, docs, cleanup and deletion are your calls. Nothing in the
repo binds you, this file included: earlier agents' choices are a starting
point, not rules. Change or delete whatever you think is wrong, and leave the
repo the way you'd want the next agent to find it.

The one limit: **nothing leaves this repo without the owner's permission.**
Commits, issues and the repo's own demo site are yours. Upstream issues or
PRs, published packages, posts and any other outside action need the owner's
go-ahead. The repo and the site (<https://code.sargunv.dev/orbis/>, deployed
on every push to `main`) are public, so never put secrets or private
references in either.

Keep history out of the tree; git has it. Don't accumulate plans, decision
logs or research notes. Write docs that describe what is, and delete them
when they stop being true.

## Layout

```
crates/    orb-* crates (each Cargo.toml's description says what it is) and
           diplomat-swift-kotlin, the binding emitters
xtask/     build, test, bench, demo and pages tasks
web/       the `orbis` TypeScript package and the demo site
hosts/     Android, Apple and desktop host shells
fixtures/  the GL JS and MapLibre Native test-suite mirrors, fetched by
           `cargo xtask fixtures`
scripts/   helpers shared across languages (Android device access)
```

Playwright.

| `cargo xtask rt [--suite render\|query\|native-render\|native-query\|native-expression] [--filter <s>] [--platform native\|chrome\|all]` | the GL JS render or query fixtures, or MapLibre Native's render, query or expression suites (the ones mln-rs runs), graded as Native's runner grades them |
| `cargo xtask support` | `docs/style-support.md`, the generated style support matrix (previews, phases, and per property what the spec, GL JS, Native and Orbis accept, with fixture results); run it after a full fixture run |
| `cargo xtask sweep [--dry-run] [--keep-hours N]` | prune stale build artifacts when the disk runs low |

## Changing a dependency

Don't vendor dependencies. To change one, fork it to `github.com/sargunv/`,
put the change on a branch there, and point Cargo at it with
`[patch.crates-io]` (a `git` URL and `branch`; `Cargo.lock` pins the commit).
Add the upstream fix to #35 so the patch can go once it's released.

## The machine

Several agent sessions often share this machine.

- Make temporary files with `mktemp`, never fixed names in `/tmp`.
- The disk is shared: keep one `target/` per worktree, run
  `cargo xtask sweep` when space runs low, and delete only what you made.
- Builds share one compiler cache: `~/.cargo/config.toml` wraps rustc in
  sccache (60 GiB). Dependencies compiled in one worktree are reused by the
  next; don't set `CARGO_TARGET_DIR` as an environment variable, which
  changes the cache keys (use `--target-dir`).
- Shell tools move a command to the background when it outlives the call's
  timeout (two minutes by default), and nothing wakes you when it ends. Give
  builds, checks and fixture runs the longest timeout allowed, and wait for
  anything that still lands in the background.
- Android: `scripts/android-serial` gives this worktree's emulator through
  `devices-cli`. Physical phones (a moto g and a Galaxy Z Fold 7) are shared:
  `devices-cli assign <serial>` first, touch only a phone you hold, and
  `devices-cli release` right after.
- Commit and push straight to `main`. There are no PRs and no CI; the one
  workflow publishes the demo.

## Commits

Subjects follow [Conventional Commits](https://www.conventionalcommits.org/):
`type(scope): summary`, all lowercase after the colon except proper names,
with no trailing period.

- Types: `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`,
  `chore`. Mark a breaking change to the public API with `!`.
- The scope is the crate without its `orb-` prefix (`render`, `symbol`,
  `camera`), or `web`, `demo`, `xtask`, `fixtures` or `hosts`. Leave it out
  when a change spans many.
- The body is prose: what changed and why, with measured numbers where they
  matter. The subject says what; the body says why.

For example: `fix(source): request a failed tile's parent instead of leaving
a hole`.

## Notes from earlier agents

Advice that cost time to learn, not rules:

- What a frame shows should never depend on how the camera got there: once
  its data has loaded, a map reached by a gesture looks like a fresh one at
  that camera. Breaking this caused many bugs; the path tests in `orb-api`
  check it. Spreading load work across frames is fine as a last resort,
  after other performance techniques hit a wall, as long as the result
  doesn't depend on the path. One exception, by the owner's choice:
  MapLibre Native's label stabilisers (previous anchor first, shown labels
  placed first in tilted views, no further) are a map option, on by default for continuous maps. The path
  tests run with it off.
- Fix causes rather than hiding them behind fades, fallbacks or flattening.
- GL JS (with its fixtures) and MapLibre Native are both guides to correct
  behaviour, not pixel targets, and neither is assumed better. Measure both
  and aim for whichever does a thing best. Orbis is a next-generation
  MapLibre renderer, not a GL JS port: "GL JS does it too" is never enough
  reason to design, keep, defer or close something. Check what Native does
  (mln-rs is a readable port of it) and take the better of the two.
- `cargo xtask check --affected` is the fast loop; run the fixtures now and
  then.
- On tile-based GPUs (Apple, phones), per-pass GPU timestamps show where
  work waits, not where it is. Compare whole-frame times.
- Burn issues down rather than piling them up. The focus is performance,
  size, style parity and clean, modern Rust. Fix small follow-ups in the
  same piece of work. File an issue only for something substantial in that
  focus, and drop the rest with a line in the commit or the closing comment.
- Label an issue `blocked` only when it needs the owner (their hardware,
  accounts or a decision) and nothing in it can move without them. Split
  the owner's part into its own issue so the rest stays workable.
- Put screenshots in issues with `gh issue comment <n> --attach ./shot.png#alt`
  (or `gh issue create … --attach`), cropped to the map. Never push branches
  or commits to host media.
- Keep tracking issues easy to scan: what's open on top. Remove finished
  entries, or move them into a short "Done" list at the bottom, rather than
  leaving them ticked in place.
- Other sessions' builds make wall times noisy. Compare a change in one
  session, interleaved: `cargo xtask bench … --compare origin/main` or
  `cargo xtask h2h … --compare origin/main`, with `h2h stills --diff
  target/h2h/png` to check both builds draw the same. Instructions retired (the
  stills table, or `/usr/bin/time -l` around any run) barely move with
  load. CPU times move too: under load more work lands on efficiency
  cores, where the same work takes 1.5–2.5× the CPU time.
