# Orbis

An experimental, ground-up Rust renderer for the MapLibre v8 style spec, built
and steered entirely by AI agents. One core renders on wgpu: in the browser
through wasm and WebGPU (WebGL 2 where WebGPU has no adapter), and natively
through Vulkan, Metal and D3D12.

Its aim is to be a modern, next generation renderer able to develop quickly,
support new features, and perform better than the existing renderers
(maplibre-native, maplibre-gl-js, mln-rs) on download size, load time, tile
processing and rendering speed, in 2D and 3D, while drawing v8 styles correctly.

Scope is all of the approved v8 spec; what the architecture gives for free
without new syntax; projections, coordinate reference systems and tile matrix
sets; and style-spec proposals. Nothing else belongs: Orbis invents no style
syntax of its own beyond projections, CRS and tile matrix sets, so lighting
models, effects and paint properties no approved spec or proposal defines stay
out.

- Syntax beyond the approved spec (proposals, projections, CRS and tile matrix
  sets) sits behind the preview switch (#134), off unless a map opts in, so a
  style never depends on it by accident: a new key, value or expression is a
  `Preview` in `orb-style`, gated where its input parses.
- What the architecture gives for free adds no syntax and is always on:
  transitions on anything practical, and inputs a property's evaluation phase
  can honour beyond the spec (its table entry's `extends`), such as data and
  camera inputs. Where GL JS or Native would reject such a style, for example a
  data-driven expression on a property the spec keeps constant, Orbis draws it
  and warns once that it isn't portable.
- Every key, value and layer type the approved spec doesn't define is an Orbis
  extension, whether we invented it or took it from an unapproved proposal, and
  is named in reverse-DNS form, as the maplibre-native-ffi plugin API names
  plugin layers: keys, properties and values as `dev.sargunv.orbis:<name>`, new
  layer types as `dev.sargunv.orbis.<name>`, and the preview that gates each by
  the same name. A proposal's entry in `docs/style-support.md` links the
  proposal; once the spec approves it, the spec's name replaces ours. CRS
  identifiers (`EPSG:3413`, PROJ parameters) stay as their standards define
  them.

`docs/style-support.md`, generated by `cargo xtask support`, lists the previews
and what each property accepts.

Orbis's public API is
[maplibre-native-ffi](https://github.com/maplibre/maplibre-native-ffi)'s C API
(#116): `orb-ffi` builds it on `orb-api` as the `maplibre-native-c` library
mln-ffi's bindings load, at the mln-ffi commit `xtask/src/mln_ffi.rs` pins.

## Layout

```
crates/    orb-* crates (each Cargo.toml's description says what it is)
xtask/     build, check, fixture, bench and pages tasks
web/       the `orbis` TypeScript package, the demo site and the page scripts
hosts/     the Android app's Gradle packaging (its code is orb-android)
fixtures/  the GL JS, MapLibre Native and maplibre-native-ffi mirrors, fetched
           by `cargo xtask fixtures`
scripts/   helpers shared across languages (Android device access)
```

## Commands

`mise install` provides the pinned tools; `mise run` and `mise x` install
`web/`'s packages when its lockfile changes. dprint formats every language
(rustfmt, oxc for the web, Markdown, TOML and YAML, ktfmt, ruff): `dprint fmt`
applies it, `mise run check` runs it with jactionlint, shellcheck, vite-plus's
lint and clippy, and `mise run fix` fixes what they can.
`mise run demo:desktop [scene|style URL] [--at …]` opens the native demo window,
and `mise run demo:web [vite options]` builds `core.wasm` and serves the web
demo.

What a change is checked and measured by: `cargo xtask check` and the fixtures
(`cargo xtask rt`) for correctness, `pnpm -C web e2e` for the web package,
`cargo xtask bench --compare` and `cargo xtask h2h` for native speed, and
`pnpm -C web session` with `cargo xtask bench session` for a user's first
session in each browser and natively. The rest are diagnostics.

Environment knobs for any native run: `ORB_BACKEND=vulkan|metal|dx12|gl` picks
wgpu's back end (`gl` where wgpu has GLES, as on Android); `ORB_DRIVER=cpu` or
`cpu-tex` puts the device on WebGL 2's CPU frame driver, its tables in storage
buffers or data textures, and `webgl2` on everything else WebGL 2 lacks too
(compute, so drawn mips, and its gaps); `ORB_TEXTURE_SIDE=4096` stands in for a
device whose 2D textures stop at that side; `ORB_COMPILES_HOLD_PRESENTS=1`
stands in for Firefox's WebGPU, whose compiles hold its presents, so a map
compiles its whole set at once and draws nothing while one runs;
`ORB_GPU_CAPTURE=n` captures frame n in the graphics debugger the process runs
under.

## Changing a dependency

Don't vendor dependencies. To change one, fork it to `github.com/sargunv/`, put
the change on a branch there, and point Cargo at it with `[patch.crates-io]` (a
`git` URL and `branch`; `Cargo.lock` pins the commit). Add the upstream fix to
#35 so the patch can go once it's released.

## The machine

Several agent sessions often share this machine.

- Make temporary files with `mktemp`, never fixed names in `/tmp`.
- The disk is shared: keep one `target/` per worktree, run `cargo xtask sweep`
  when space runs low, and delete only what you made.
- Builds share one compiler cache: `~/.cargo/config.toml` wraps rustc in sccache
  (60 GiB). Dependencies compiled in one worktree are reused by the next; don't
  set `CARGO_TARGET_DIR` as an environment variable, which changes the cache
  keys (use `--target-dir`).
- Shell tools move a command to the background when it outlives the call's
  timeout (two minutes by default), and nothing wakes you when it ends. Give
  builds, checks and fixture runs the longest timeout allowed, and wait for
  anything that still lands in the background. macOS has no `timeout`; use
  `perl -e 'alarm N; exec @ARGV' …`.
- Android: `scripts/android-serial` gives this worktree's emulator through
  `devices-cli`. Physical phones (a moto g and a Galaxy Z Fold 7) are shared:
  `devices-cli assign <serial>` first, touch only a phone you hold, and
  `devices-cli release` right after.
- Commit and push straight to `main`. There are no PRs and no CI; the one
  workflow publishes the demo.

## Commits

Subjects follow [Conventional Commits](https://www.conventionalcommits.org/):
`type(scope): summary`, all lowercase after the colon except proper names, with
no trailing period.

- Types: `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`, `chore`.
  Mark a breaking change to the public API with `!`.
- The scope is the crate without its `orb-` prefix (`render`, `symbol`,
  `camera`), or `web`, `demo`, `xtask`, `fixtures` or `hosts`. Leave it out when
  a change spans many.
- The body is prose: what changed and why, with measured numbers where they
  matter. The subject says what; the body says why.

For example:
`fix(source): request a failed tile's parent instead of leaving a hole`.

## Notes from earlier agents

Advice that cost time to learn, not rules:

- What a frame shows should never depend on how the camera got there: once its
  data has loaded, a map reached by a gesture looks like a fresh one at that
  camera. Breaking this caused many bugs; the path tests in `orb-api` check it.
  Spreading load work across frames is fine as a last resort, after other
  performance techniques hit a wall, as long as the result doesn't depend on the
  path. One exception, by the owner's choice: MapLibre Native's label
  stabilisers (previous anchor first, shown labels placed first in tilted views,
  no further) are a map option, on by default for continuous maps. The path
  tests run with it off.
- Fix causes rather than hiding them behind fades, fallbacks or flattening.
- GL JS (with its fixtures) and MapLibre Native are both guides to correct
  behaviour, not pixel targets, and neither is assumed better. Measure both and
  aim for whichever does a thing best. Orbis is a next-generation MapLibre
  renderer, not a GL JS port: "GL JS does it too" is never enough reason to
  design, keep, defer or close something. Check what Native does (mln-rs is a
  readable port of it) and take the better of the two.
- `cargo xtask check --affected` is the fast loop; run the fixtures now and
  then.
- WebGL 2 shares the renderer, the shaders and every render pass with WebGPU;
  only the frame driver differs (`orb-render`'s `driver/gpu.rs` and
  `driver/cpu.rs`). Checks in `xtask check` keep it that way. A feature born in
  compute, indirect draws or storage fails xtask's `GPU_ONLY_FILES` rule until
  its file is listed with what stands in for it on WebGL 2, or the `Gap` it
  reports. A shader that breaks GLSL ES 3.00, WebGL 2's limits (15 varyings, 16
  textures, 16 KiB uniform blocks) or ANGLE's uniform layout fails
  `orb-shaders`' dry run on your machine, as does a flat varying that isn't
  `flat, either` (GL takes the last vertex's value). WebGL 2 and native GL ES
  compile GLSL that `orb-shaders`' build script writes (`glsl`), not wgpu's
  translation at load, so GL's GLSL changes go there or in naga's writer. The
  two drivers are held word for word by `orb-runtime`'s `drivers` test, so a
  change to `driver/cpu.rs` should say in its commit why the GPU driver needs no
  twin of it.
- The web's builds write a derived `Debug` as its type's or variant's name alone
  (`-Zfmt-debug=shallow`, `xtask/src/web.rs`), so code that compares, hashes or
  parses `{:?}` output works natively and breaks only on the web. Compare with
  `PartialEq`, and give what a message must show a `Display`.
- Firefox with a WebGPU adapter draws with WebGPU, by measurement (cold
  `pnpm session` runs on Firefox 159): its WebGL 2 drew a first frame sooner but
  filled the view's centre later on every session, answered moves later, and
  uploaded 2–3× the bytes, because Firefox's WebGL has no
  `KHR_parallel_shader_compile` (every program links on the thread that draws)
  and no `EXT_clip_control` (the `depth-precision` gap). Retest both backends
  (`pnpm session --browser=firefox`, with `--backend=webgl2` beside the default)
  once Firefox ships either extension, or a WebGPU that compiles off the thread
  that presents (`Caps::compiles_hold_presents`).
- When a feature puts nontrivial work on a hot path (frames, tile arrival, first
  use), a focused bench of it on against off pays for itself; most features
  don't need one. Measure it moving, not only at rest: what a pass costs as a
  city's buildings arrive mid-zoom is what stutters.
- On tile-based GPUs (Apple, phones), a pass's start timestamp lands when its
  vertex work starts, ahead of the fragment work of the passes before it, the
  frame before's included where two are in flight. orb-hal-wgpu times each pass
  from its start or the previous pass's end, whichever is later, which Xcode's
  Metal System Trace (`xcrun xctrace record --template 'Metal System Trace'`)
  agrees with; raw spans read about twice the work. Chrome paced at 60 Hz runs a
  light frame's GPU at low clocks, two to three times slower than the same work
  unpaced: compare engines unpaced, at equal pixels (GL JS caps its canvas at
  `maxCanvasSize`, 4096 a side by default). `fill_floor` (orb-hal-wgpu's
  example) times what any full-screen pass costs on the device.
- Size, performance, simplicity and correctness all count at once: take the best
  design, not the one that games a number. The build's watch levels are
  tripwires for a look, not budgets, and room under one isn't margin to spend.
- GPU memory has no budget: it is as slim as the view lets it be. Pools, pages
  and atlases hold what the view needs, packed exactly, and grow as uploads need
  them, whatever the camera does: the vertex and index pools by adding a block,
  which copies nothing (`orb-render`'s scene), so nothing in the renderer knows
  about gestures. A node draws once a block, so what draws as points (circles,
  heatmaps, symbols), whose tiles' draws overlap, keeps to one block that moves
  as it grows: blocks that split a node's tiles would let the order tiles
  arrived in decide what is on top. What's kept of tiles out of view (the tile
  cache, parked payloads) is bounded by the tiles the view draws, and goes first
  on a platform's low-memory warning or an allocation the device refuses. A cap
  that coarsens or drops what a view draws, or sizes from a share of a fixed
  number, is the wrong tool: being slim is what keeps a phone's context.
- Burn issues down rather than piling them up. The focus is performance, size,
  style parity and clean, modern Rust. Fix small follow-ups in the same piece of
  work. File an issue only for something substantial in that focus, and drop the
  rest with a line in the commit or the closing comment.
- Label an issue `blocked` only when it needs the owner (their hardware,
  accounts or a decision) and nothing in it can move without them. Split the
  owner's part into its own issue so the rest stays workable.
- Put screenshots in issues with `gh issue comment <n> --attach ./shot.png#alt`
  (or `gh issue create … --attach`), cropped to the map. Never push branches or
  commits to host media.
- Keep tracking issues easy to scan: what's open on top. Remove finished
  entries, or move them into a short "Done" list at the bottom, rather than
  leaving them ticked in place.
- Other sessions' builds make wall times noisy. Compare a change in one session,
  interleaved: `cargo xtask bench … --compare origin/main` or
  `cargo xtask h2h … --compare origin/main`, with
  `h2h stills --diff target/h2h/png` to check both builds draw the same.
  Instructions retired (the stills table, or `/usr/bin/time -l` around any run)
  barely move with load. CPU times move too: under load more work lands on
  efficiency cores, where the same work takes 1.5–2.5× the CPU time.
- A measurement harness or option earns its place by being run: delete one that
  answered its question, and lean on the gated tools above before writing
  another. Git keeps the deleted ones
  (`git log --diff-filter=D -- web/scripts`).
